## 2. נוהל אבטחת מידע (תקנה 4)

**אמצעים קיימים במערכת**
- HTTPS בלבד; עוגיית סשן httpOnly, sameSite=lax, secure; CSP קשיח; חסימת טפסים חוצי-אתרים.
- הפרדה מלאה בין חשבונות — כל שאילתה מסוננת לפי השליח.
- קודי כניסה מגובבים (bcrypt), קוד חד-פעמי ב-SMS עם מגבלת ניסיונות, הגבלת קצב לכניסה ולהגדרות, ניתוק מכשירים בהחלפת קוד/נייד.
- יומן פעולות ללא שמות/טלפונים/תוכן (נשמר 180 יום); המנהל רואה נתונים מצטברים בלבד.
- חשבון ההדגמה רץ בטרנזקציה שמבוטלת — לא נשמר דבר ולא נשלח SMS.

**חובות תפעוליות (לביצוע ע"י המפעיל)**
- [ ] להפעיל אימות דו-שלבי (MFA) בחשבון Railway ובחשבון GitHub.
- [ ] סיסמת מנהל (ADMIN_PASSWORD) ו-SESSION_SECRET חזקים, שמורים רק ב-Railway; להחליף אם יש חשד לדליפה.
- [ ] להפעיל גיבויים ב-Railway למסד הנתונים, ולבדוק שחזור לפחות פעם ברבעון. לתעד כאן תאריך בדיקה אחרון: ______
- [ ] לאמץ את ה-DPA של Railway (railway.com/legal/dpa) ולשמור עותק חתום/מאושר.
- [ ] לשקול חתימה על הסכם מחזיק/סודיות עם ימות המשיח.
- [ ] לעדכן תלויות (npm audit) ולבדוק את יומן "תקלות" בממשק הניהול לפחות פעם בחודש.
- [ ] סקירת אבטחה שנתית — לתעד תאריך וממצאים בקובץ זה.

## 3. נוהל אירוע אבטחה (תקנה 11)

1. **זיהוי** — חשד לגישה לא מורשית, דליפה, אובדן מידע או השבתה (מקור: יומן תקלות, התראת Railway, דיווח משתמש).
2. **בלימה מיידית** — החלפת ADMIN_PASSWORD / SESSION_SECRET (מנתק את כולם), השבתת חשבון שנפרץ, עצירת השירות אם צריך.
3. **תיעוד** — מה קרה, מתי, אילו חשבונות ונתונים הושפעו, מה נעשה (טבלה למטה).
4. **הודעה לשלוחים שנפגעו** — בהקדם, עם הסבר מה נחשף ומה לעשות.
5. **דיווח לרשות להגנת הפרטיות** — באירוע אבטחה חמור, ללא דיחוי (טופס מקוון ב-gov.il).
6. **הפקת לקחים** — תיקון השורש ועדכון הנוהל.

## 4. טיפול בבקשות עיון / תיקון / מחיקה

- בקשות מגיעות דרך טופס "יצירת קשר" (/contact; מטופס הרישום הקישור מזהה את השליח) ונשמרות בדף "פניות" של המנהל. המפעיל מעביר לשליח הרלוונטי תוך 3 ימי עבודה (כפתור "העברה לשליח") ומסמן "טופל".
- השליח מטפל דרך כרטיס המקורב (עריכה/מחיקה) או שולח ייצוא CSV.
- זמן מענה מירבי: 30 יום.
